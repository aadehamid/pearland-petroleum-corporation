## 2. Per-store backup, recovery, and `exe.dev` sizing matrix

To satisfy `ADR-0051` and `ADR-0055` (`RPO` = zero silent loss of committed world checkpoints and source outboxes; `RTO <= 1 hour` for Slice 1 data volume up to 12 months of Refinery A history, `< 5 GB` compressed), every runtime store declares its backup mechanism and RAM footprint. All SQLite Litestream and WAL syncs run on a `60-second` sync cadence (checked against the Cloudflare R2 free-tier monthly write-operation allowance during `WP-4A` so sync volume never exhausts free-tier limits):

| Store / service | Placement (Slice 1, `ADR-0055`) | Backup & recovery mechanism | Target RPO | Est. RAM floor |
|---|---|---|---|---|
| Cloudflare R2 (raw, Delta, checkpoints, manifests, `telemetry/otel/`, `evaluation/hidden/`) | Managed object store (permitted free-tier exception, `T79`) | Object versioning + immutable manifests; authoritative rebuild source | 0 (durable commit) | n/a |
| PostgreSQL (CTRM + TimescaleDB + pgvector + Dagster metadata + Silver staging/inbox + workflow/approval/LangGraph checkpoints) | `exe.dev` 12 GB VM (or 8 GB VM A Stores fallback) | WAL archiving (60 s archive timeout) + scheduled `pg_basebackup` to R2; post-restore outbox-sequence vs `InboxReceipt` high-water-mark check | <= 5 min / last WAL (gap flagged as `RECOVERY_GAP`) | 2.2 GB |
| MySQL (Logistics + outbox) | `exe.dev` 12 GB VM (or 8 GB VM A Stores fallback) | Binary log (`binlog`) archiving (60 s flush) + scheduled dump to R2; post-restore outbox-sequence vs `InboxReceipt` check | <= 5 min / last binlog (gap flagged as `RECOVERY_GAP`) | 1.0 GB |
| SQLite (Refinery/LIMS edge + outbox) | `exe.dev` 12 GB VM (or 8 GB VM A Stores fallback) | Litestream WAL replication (`60 s` sync cadence, R2 op-budget checked in `WP-4A`) to R2; post-restore outbox-sequence vs `InboxReceipt` check | <= 1 min (gap flagged as `RECOVERY_GAP`) | 0.2 GB |
| Neo4j Community (instance graph projection) | `exe.dev` 12 GB VM (or 8 GB VM A Stores fallback) | Persistent `/data` mount + offline `neo4j-admin database dump` to R2; fully rebuildable from Delta + Turtle | Rebuildable from R2 | 2.5–3.5 GB |
| NATS JetStream (IT event transport) | `exe.dev` 12 GB VM (or 8 GB VM A Stores fallback) | Stream state backed by durable source outboxes (disposable/re-publishable from Postgres/MySQL/SQLite outboxes + R2 raw) | 0 (re-derived from outbox) | 0.2 GB |
| Mosquitto (OT Sparkplug B) | `exe.dev` 12 GB VM (or 4 GB VM B Apps fallback) | Persistent session store + R2 L0 raw backfill (`OT-001`) | Backfilled from historian/R2 | 0.1 GB |
| Dagster webserver + daemon + FastAPI + Dash + MLflow + lightweight OTel Collector | `exe.dev` 12 GB VM (or 4 GB VM B Apps fallback) | Stateless containers; metadata/workflow state in Postgres; OTLP JSON shipped hourly to R2 `telemetry/otel/` (queried by DuckDB for leak tests) | 0 (Git + Postgres + R2) | 2.2–2.7 GB |
| Self-hosted Langfuse v3 (web + worker + ClickHouse + Redis) | **Staged to `WP-7`** (`ADR-0055` `G2-b`; requires dedicated `16 GB` two-VM split when activated) | ClickHouse/Postgres snapshots to R2 (telemetry only, non-authoritative) | Best-effort | Staged (`5.0–6.0 GB` in `WP-7`) |

**Sizing and gap-detection conclusion (`ADR-0055`):** Slice 1 runs on **one `12 GB` `exe.dev` VM** (or two VMs, `8 GB` stores plus `4 GB` apps, with identical Docker Compose files if `exe.dev` cannot allocate 12 GB on one VM) with active service floors totaling `8.4–9.9 GB` leaving OS/kernel headroom. ClickHouse-backed Langfuse v3 moves to `WP-7`, no local Ollama runs on these VMs, and Cloudflare D1 is retired for v1 in favor of PostgreSQL. On restore, every WAL/binlog restore compares each source outbox's highest committed sequence number against PostgreSQL `InboxReceipt` high-water marks and R2 raw event logs; any missing tail within the RPO window raises an explicit `RECOVERY_GAP` halt rather than silently dropping events.

## 4. Paper end-to-end boundary walkthrough tests

### Walkthrough A — Delayed LIMS lab correction across system boundaries (`UC-2`, Scenario B IDs `S2-*`)

All publication, receipt, and release IDs below belong exclusively to Scenario B (`SCENARIO-001 §3`, prefixed `S2-`) so they never collide with `INFO-001 §3` (`P0`/`P1`/`P2`) or `DATA-001 §2` (`L1`/`X1`).

1. **08:00 UTC (Effective — segregated receipt):** A scaled `SYNTHETIC` arithmetic test lot `LOT-44` (`500 bbl` — labeled as a small arithmetic fixture; real Gulf Coast pipeline batches are $\ge 50\text{ kbbl}$ and marine cargoes $\ge 300\text{ kbbl}$) arrives into **segregated holding tank `TK-101H`** (never commingled with active crude tank heels before quality release). `WORLD-001` commits exact physical mass via `EQ-01`.
2. **08:05 UTC (Logistics):** MySQL Logistics commits custody ticket `S2-M1` (`500 bbl`) and inserts `OutboxEntry(delivery_key="log:S2-M1:v1", digest=H1)` in the same DB transaction; NATS JetStream delivers `S2-M1`.
3. **09:00 / 09:20 / 09:30 / 09:50 UTC (LIMS initial result & analytical cut):** SQLite LIMS records failed assay `S2-P1` at `09:00` (referring to 08:00 sample), publishes `S2-P1` at `09:20`, and delivers receipt `S2-R1` to `planner/workspace` at `09:30`. `LOT-44` stays in `TK-101H` under `QUALITY_HOLD`; CTRM holds trade actualization (physical stock is in `TK-101H`; commercial available crude excludes `LOT-44`). Dagster publishes analytical `ReleaseManifest S2-L1` at `09:45`, delivered to `planner/workspace` at `09:50` (`09:50 <= 10:00`).
4. **10:00 UTC (Planner decision):** Planner queries workspace at cutoff `10:00`. Under `INFO-001 §3` and `SCENARIO-001 §3`, both `S2-P1` (`09:30 <= 10:00`) and `S2-L1` (`09:50 <= 10:00`) are eligible. Planner runs the Pyomo Planning LP (`ModelRun` pinned to `S2-L1` and `S2-P1`) and records `DecisionDossier S2-D1`.
5. **12:00 / 12:30 / 13:00 UTC (Delayed LIMS correction `S2-P2`):** LIMS discovers lab instrument bias, records passing revision `S2-P2` (superseding `S2-P1`, ordinal 2) at `12:00`, publishes at `12:30`, and delivers receipt `S2-R2` at `13:00`.
   - **Original fact owner:** SQLite LIMS (`S2-P1`, immutable).
   - **Correction authority:** SQLite LIMS via immutable successor `S2-P2` only.
   - **Revision consumer:** Atomic Postgres staging + `delta-rs` publish emits restated `ReleaseManifest S2-L2` (published `13:10`, delivered `13:15`); CTRM releases `LOT-44` from `TK-101H` and actualizes the trade.
   - **Decision replay:** Replaying `DecisionDossier S2-D1` pins cutoff `10:00` and `ReleaseManifest S2-L1`; `S2-R2` (`13:00 > 10:00`) and `S2-L2` (`13:15 > 10:00`) are ineligible and undisclosed. If no publication qualifies, return strictly `UNRESOLVED`; if accessible evidence cannot answer a claim, label the claim `UNKNOWN`.

### Walkthrough B — Duplicated crude movement with atomic inbox/staging boundary (`UC-2` / `INT-RETRY-01` / `PO-03`)

1. **08:05 UTC:** MySQL Logistics commits movement `M1` (`+200 bbl` into `TK-101H`, opening `1,000 bbl`, with `150 bbl` dispatch `M2` already applied) plus `OutboxEntry(delivery_key="log:M1:v1", digest=H1)`.
2. **08:06 UTC (Crash after atomic staging commit, before NATS ack):** Consumer executes **one PostgreSQL ACID transaction** that inserts `M1` into Silver staging **and** records `InboxReceipt(delivery_key="log:M1:v1", digest=H1, status="APPLIED")`, then crashes before sending NATS ack. Because staging and receipt share one ACID transaction, a crash can never leave one written without the other.
3. **08:07 UTC (Duplicate redelivery):** NATS JetStream redelivers `log:M1:v1` (`H1`). Consumer checks `InboxReceipt`, finds `(log:M1:v1, H1)` already `APPLIED`, returns the prior receipt, and adds `0 bbl`. Downstream `delta-rs` publication uses idempotent Delta transaction metadata (`txnAppId` + deterministic `txnVersion` from staged batch ID) with `aws_conditional_put="etag"` so a crash during R2 Delta commit also yields one business effect (`1,050 bbl`, never `1,250 bbl`).
4. **08:08 UTC (Conflicting payload injection):** A replay sends `log:M1:v1` with digest `H2 != H1`. Consumer rejects the mutation, routes the envelope to `QUARANTINED`, leaves stock at `1,050 bbl`, and blocks `ReleaseManifest` publication until resolved.
5. **Analytical rebuild:** Rebuilding Delta Gold and Neo4j from R2 raw archives replays projections only and never invokes the canonical world engine.
