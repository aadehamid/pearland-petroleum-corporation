## 1. Refinery operational & business functions versus PPC representations

A refinery's business function is independent of the software product chosen to simulate or connect it (`ADR-0041`). Every active and staged component below complies with the no-paid-commercial-license rule (`T52`), with Cloudflare R2 as the explicit permitted free-tier exception (`T79`).

## 2. Per-store backup, recovery, and `exe.dev` sizing matrix

To satisfy `ADR-0051` (`RPO` = zero silent loss of committed world checkpoints and source outboxes; `RTO <= 1 hour` for Slice 1 data volume up to 12 months of Refinery A history, `< 5 GB` compressed), every runtime store declares its backup mechanism and RAM footprint:

| Store / service | Placement | Backup & recovery mechanism | Target RPO | Est. RAM floor |
|---|---|---|---|---|
| Cloudflare R2 (raw, Delta, checkpoints, manifests, `evaluation/hidden/`) | Managed object store (permitted free-tier exception, `T79`) | Object versioning + immutable manifests; authoritative rebuild source | 0 (durable commit) | n/a |
| PostgreSQL (CTRM + TimescaleDB + pgvector + Dagster metadata + Silver staging/inbox) | `exe.dev` VM A (Stores) | Continuous WAL archiving + scheduled `pg_basebackup` to R2 | <= 5 min / last WAL | 2.0 GB |
| MySQL (Logistics + outbox) | `exe.dev` VM A (Stores) | Binary log (`binlog`) archiving + scheduled logical/physical dump to R2 | <= 5 min / last binlog | 1.0 GB |
| SQLite (Refinery/LIMS edge + outbox) | `exe.dev` VM A (Stores) | Litestream continuous WAL replication (or transactional snapshot) to R2 | <= 1 min | 0.2 GB |
| Neo4j Community (instance graph projection) | `exe.dev` VM A (Stores) | Persistent `/data` mount + offline `neo4j-admin database dump` to R2; fully rebuildable from Delta + Turtle | Rebuildable from R2 | 2.5–4.0 GB |
| NATS JetStream (IT event transport) | `exe.dev` VM A or B | Stream state backed by durable source outboxes (disposable/re-publishable from Postgres/MySQL/SQLite outboxes + R2 raw) | 0 (re-derived from outbox) | 0.2 GB |
| Mosquitto (OT Sparkplug B) | `exe.dev` VM B (Apps) | Persistent session store + R2 L0 raw backfill (`OT-001`) | Backfilled from historian/R2 | 0.1 GB |
| Dagster webserver + daemon + FastAPI + Dash | `exe.dev` VM B (Apps) | Stateless containers; metadata in Postgres | 0 (Git + Postgres) | 1.5–2.0 GB |
| Self-hosted Langfuse v3 (web + worker + ClickHouse + Redis) | `exe.dev` VM B (or staged WP-7; lightweight OTel collector in Slice 1) | ClickHouse/Postgres snapshots to R2 (telemetry only, non-authoritative) | Best-effort | 5.0–6.0 GB (ClickHouse >= 4 GB) |
| Cloudflare D1 (workflow/approval state — if retained over Postgres) | Cloudflare managed SQLite | Scheduled D1 export snapshots to R2 (or consolidate into Postgres on VM A in WP-0) | Scheduled export | n/a |

**Sizing conclusion:** Running the full Slice 1 stack **with** self-hosted Langfuse v3 (ClickHouse + Redis) requires **12 to 16 GB RAM** before any local Ollama LLM, favoring either a two-VM `exe.dev` split (VM A Stores + VM B Apps/Observability) or running a lightweight OTel JSON/Postgres trace collector in Slice 1 and standing up ClickHouse-backed Langfuse v3 in WP-7. This sizing trade-off is surfaced as an explicit WP-0 owner choice below.

## 4. Paper end-to-end boundary walkthrough tests

### Walkthrough A — Delayed LIMS lab correction across system boundaries (`UC-2`)

1. **08:00 UTC (Effective — segregated receipt):** A scaled `SYNTHETIC` arithmetic test lot `LOT-44` (`500 bbl` — labeled as a small arithmetic fixture; real Gulf Coast pipeline batches are $\ge 50\text{ kbbl}$ and marine cargoes $\ge 300\text{ kbbl}$) arrives into **segregated holding tank `TK-101H`** (never commingled with active crude tank heels before quality release). `WORLD-001` commits exact physical mass via `EQ-01`.
2. **08:05 UTC (Logistics):** MySQL Logistics commits custody ticket `M1` (`500 bbl`) and inserts `OutboxEntry(delivery_key="log:M1:v1", digest=H1)` in the same DB transaction; NATS JetStream delivers `M1`.
3. **09:00 / 09:20 / 09:30 UTC (LIMS initial result):** SQLite LIMS records failed assay `P1` at `09:00` (referring to 08:00 sample), publishes `P1` at `09:20`, and delivers receipt `R1` to `planner/workspace` at `09:30`. `LOT-44` stays in `TK-101H` under `QUALITY_HOLD`. CTRM holds trade actualization; physical stock is present in `TK-101H`, commercial available crude excludes `LOT-44`.
4. **10:00 UTC (Planner decision):** Planner queries workspace at cutoff `10:00`. `INFO-001 §3` returns `P1` (`09:30 <= 10:00`). Planner runs the Pyomo Planning LP (`ModelRun` pinned to `ReleaseManifest L1` and `P1`) and records `DecisionDossier D1`.
5. **12:00 / 12:30 / 13:00 UTC (Delayed LIMS correction `P2`):** LIMS discovers lab instrument bias, records passing revision `P2` (superseding `P1`, ordinal 2) at `12:00`, publishes at `12:30`, and delivers receipt `R2` at `13:00`.
   - **Original fact owner:** SQLite LIMS (`P1`, immutable).
   - **Correction authority:** SQLite LIMS via immutable successor `P2` only.
   - **Revision consumer:** Atomic Postgres staging + `delta-rs` publish emits restated `ReleaseManifest L2`; CTRM releases `LOT-44` from `TK-101H` and actualizes the trade.
   - **Decision replay:** Replaying `DecisionDossier D1` pins cutoff `10:00` and `ReleaseManifest L1`; `R2` (`13:00 > 10:00`) is ineligible and undisclosed. If no publication qualifies, return strictly `UNRESOLVED`; if accessible evidence cannot answer a claim, label the claim `UNKNOWN`.

### Walkthrough B — Duplicated crude movement with atomic inbox/staging boundary (`UC-2` / `INT-RETRY-01` / `PO-03`)

1. **08:05 UTC:** MySQL Logistics commits movement `M1` (`+200 bbl` into `TK-101H`, opening `1,000 bbl`, with `150 bbl` dispatch `M2` already applied) plus `OutboxEntry(delivery_key="log:M1:v1", digest=H1)`.
2. **08:06 UTC (Crash after atomic staging commit, before NATS ack):** Consumer executes **one PostgreSQL ACID transaction** that inserts `M1` into Silver staging **and** records `InboxReceipt(delivery_key="log:M1:v1", digest=H1, status="APPLIED")`, then crashes before sending NATS ack. Because staging and receipt share one ACID transaction, a crash can never leave one written without the other.
3. **08:07 UTC (Duplicate redelivery):** NATS JetStream redelivers `log:M1:v1` (`H1`). Consumer checks `InboxReceipt`, finds `(log:M1:v1, H1)` already `APPLIED`, returns the prior receipt, and adds `0 bbl`. Downstream `delta-rs` publication uses idempotent Delta transaction metadata (`txnAppId` + deterministic `txnVersion` from staged batch ID) with `aws_conditional_put="etag"` so a crash during R2 Delta commit also yields one business effect (`1,050 bbl`, never `1,250 bbl`).
4. **08:08 UTC (Conflicting payload injection):** A replay sends `log:M1:v1` with digest `H2 != H1`. Consumer rejects the mutation, routes the envelope to `QUARANTINED`, leaves stock at `1,050 bbl`, and blocks `ReleaseManifest` publication until resolved.
5. **Analytical rebuild:** Rebuilding Delta Gold and Neo4j from R2 raw archives replays projections only and never invokes the canonical world engine.
