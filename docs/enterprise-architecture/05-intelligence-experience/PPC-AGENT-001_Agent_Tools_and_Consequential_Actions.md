## 1. Tool and authority boundary

An agent may retrieve authorized evidence, traverse a scoped graph, request governed calculations, simulate an isolated branch and recommend an option. It cannot calculate an official KPI in prose, read hidden truth during blind evaluation or turn its recommendation into approval. Under [ADR-0048](../../adr/0048-pyomo-optimization-and-langgraph-pydantic-agents.md) and [ADR-0055](../../adr/0055-slice1-hosting-observability-postgres-workflow-and-databricks-sync.md), **LangGraph** orchestrates stateful human-approval and escalation workflows persisted in **PostgreSQL on `exe.dev`** (no Cloudflare D1 in v1), **Pydantic AI** (or Pydantic-typed tool contracts) enforces strict schema-validated tool calls inside nodes, and a lightweight **OpenTelemetry Collector** writes OTLP JSON shipped hourly to R2 `telemetry/otel/` in Slice 1 (queried by DuckDB for trace-leak tests; ClickHouse-backed self-hosted Langfuse v3 stages to `WP-7`), paired with PostgreSQL/pgvector for retrieval. Golden tests run against recorded model responses; Hamid Adesokan selects the live `WP-3B` LLM endpoint before `WP-3B` starts (`ADR-0055`). Framework selection never relaxes service-side action policy.

**Authentication and role enforcement (`B14`, `N10`):** FastAPI enforces signed JWT/session authentication (Argon2id password hashes in PostgreSQL, seeded by a `WP-3B` fixture script under `api/seed_users.py` with explicit non-production accounts for each role and rotated credentials in the `exe.dev` secret store) backed by PostgreSQL `users` and `role_assignments` tables (`Shift Supervisor`, `Refinery Operations Manager`, `Commercial Manager`, `VP Supply and Operations`, `IDENTITY_STEWARD`, `Planner`, `Auditor`). Every `ToolRequest` and `ActionAuthorization` derives its verified `actor` and `role` strictly from the authenticated server session (never trusting client-supplied role headers), and PostgreSQL enforces `proposer_actor_id != approver_actor_id` in the same ACID transaction as the approval and idempotency key. Deterministic recorded model-response fixtures for golden agent tests are authored by the `WP-3B` Full-Stack/Agent Engineer under `fixtures/golden/agent_recorded_responses/` before Hamid selects the live LLM endpoint.

`ToolRequest` has request ID, subject scope, effective time, actor and delegated role, channel, purpose, tool and contract version, branch, pinned release IDs, knowledge cutoff, input digest, requested action and expiry. `ToolResponse` has result ID/status, request ID, branch ID, knowledge cutoff, provenance class, epistemic status, output classification, source/model refs, uncertainty, redaction status and audit ID. `ActionProposal` has proposal ID, decision ID, payload digest, status, authority class, proposing actor, knowledge cutoff, measurement basis and binds exact action type, target, quantity/unit, branch, expected source revisions, policy version, approver role, evidence release, expiry and idempotency key. `ActionAuthorization` has authorization ID and authorized-at time and identifies `proposal_id`, `proposal_payload_digest`, `branch_id`, `authorization_expiry`, the human/role, scope, policy check, `APPROVED|DENIED` decision and signature or equivalent audit evidence. `ActionReceipt` has receipt ID, proposal ID, authorization basis ID, idempotency key, source revisions, execution status and time, business effect ID or blocked reason, and branch. For human approval, the basis ID is the `ActionAuthorization` ID. For `AUTO_EXECUTE`, it is the immutable preapproval policy grant ID and version. A tool cannot broaden an actor's scope.

One transition event records `decision_id`, `proposal_id` when present, prior and next states for each entity, event time, actor, policy version and authorization basis. The dossier and proposal project their states from that event. A dossier without a proposal can move `OPEN → DEFERRED|ESCALATED|EXPIRED`. A linked pair follows this table; each row is one event.

| Proposal transition | Linked dossier transition | Condition |
|---|---|---|
| `DRAFT → POLICY_CHECKED` | Remains `OPEN` | Policy check is current. |
| `DRAFT|POLICY_CHECKED → DENIED|EXPIRED` | `OPEN → REJECTED|EXPIRED`, respectively | Denial and expiry stop the proposal. |
| `POLICY_CHECKED → ESCALATED` | `OPEN → ESCALATED` | A higher authority must decide through a new decision ID. |
| `POLICY_CHECKED → RECOMMENDED` | `OPEN → RECOMMENDED` | Recommendation grants no execution authority. |
| `RECOMMENDED → RECOMMENDED_ONLY` | `RECOMMENDED → RECOMMENDED_ONLY` | `RECOMMEND` ends after proposing. |
| `RECOMMENDED → APPROVED|DENIED|DEFERRED|ESCALATED|EXPIRED` | `RECOMMENDED → APPROVED|REJECTED|DEFERRED|ESCALATED|EXPIRED`, respectively | `REQUIRE_APPROVAL` binds the exact payload and approver. |
| `APPROVED → EXECUTED|FAILED|EXPIRED` | The same transition | Execution checks the authorization and source revision. |
| `POLICY_CHECKED → AUTO_EXECUTED|FAILED` | `OPEN → AUTO_EXECUTED|FAILED` | `AUTO_EXECUTE` needs an immutable preapproval basis (`PG-A0-v1`) for a bounded `0 bbl / $0` action class (`ADR-0056`). |
| `DRAFT|POLICY_CHECKED → DENIED` | `OPEN → REJECTED` | `PROHIBITED` actions (releasing `QUALITY_HOLD`, overriding bounds/assays, writing OT setpoints, touching `evaluation/hidden/`, changing policy/mappings/grants, cross-branch reuse, financial postings, or touching real systems) have no agent path and map strictly to `DENIED` (`ADR-0056` `G3-b`). |

`DENIED`, `DEFERRED`, `RECOMMENDED_ONLY`, `ESCALATED`, `EXPIRED`, `EXECUTED`, `AUTO_EXECUTED` and `FAILED` are terminal for the proposal. `REJECTED` replaces `DENIED` on the dossier. An execution failure records its reason and no business effect. Retry after a terminal state needs a new proposal and decision ID. Execution requires a current policy check, exact approved payload, valid source revision and one-time business key. A changed quantity or target invalidates approval. Numeric authority classes (`AUTO_EXECUTE`, `REQUIRE_APPROVAL` Tier 1 and Tier 2, `ESCALATE`, and `PROHIBITED` -> `DENIED`) are locked in [ADR-0056](../../adr/0056-identity-steward-action-thresholds-and-refinery-a-parameters.md) (`G3-b`, extending PPC-012). An uncertain source or unavailable approver blocks consequential execution.

## 2. Synthetic action fixture

At 10:30 UTC an agent sees an `ESTIMATED` ULSD shortfall on the derate branch and proposes a `SCENARIO_ASSUMPTION` transfer of 5,000 bbl from terminal T. The graph path supplies potential exposure; the planning tool checks inventory and route bounds. The agent may simulate it and recommend it. If policy requires a Commercial Manager, the agent returns `REQUIRE_APPROVAL`. Only that role's authorization for this exact transfer permits execution. A duplicate execution request with the same key returns the original receipt; a different payload with that key is rejected. If the approval expires or inventory revision changes, recheck and request new authority. A baseline branch action cannot use a derate branch approval.

For the historical decision check, use [INFO-001 §3](../03-enterprise-information/PPC-INFO-001_Enterprise_Ontology_Identity_and_Time.md). The tool must pass the same recipient, channel, purpose and cutoff to evidence, graph and product queries. It must not disclose an inaccessible publication in results, traces or errors.

## 3. Qualification and decisions

Test allowed read/simulate/recommend scopes, `PROHIBITED` -> `DENIED` enforcement, policy denial, approval replay, exact-payload binding, stale source revision, duplicate/conflicting key, crash after execution, branch isolation, historical cutoff, hidden-truth and restricted-trace leaks (queried via DuckDB over R2 `telemetry/otel/`). Preserve tool calls, policy versions, approval evidence and expected/observed receipts. No agent evaluation is claimed. Framework (`ADR-0048`), numeric action-class thresholds (`ADR-0056`), PostgreSQL workflow/approval channel, and OTel JSON trace retention (`ADR-0055`) are decided; live `WP-3B` LLM endpoint selection remains explicitly with Hamid Adesokan (recorded responses cover golden tests).
