## 1. Workflow boundary

Under [ADR-0047](../../adr/0047-slice1-active-core-vs-staged-apps.md) and [ADR-0052](../../adr/0052-two-stage-ux-dash-and-relate-wasm.md) (reconciling ADR-014 and T111 `EA09D-D09`), PPC uses a two-stage UX architecture: **Slice 1** ships the bounded FastAPI plus Plotly Dash workspace to prove the end-to-end decision loop, and **Slice 1.5** promotes browser-based **Relate WASM** as the business-facing **Interactive Enterprise Context Explorer** (integrated with shared agent investigation context per `EA07C-D10`) once its bounded security and Cypher compatibility gate passes. Apache Superset (`ADR-013`) and Grafana OSS (`PPC-009`) are staged for later multi-KPI scorecard and observability phases, while Databricks AI/BI remains the strategic managed analytics platform (`EA06A-D06`, [ADR-0045](../../adr/0045-delta-lake-on-r2-and-databricks-portability.md)). A workspace presents a selected world branch, release and historical cutoff. It separates source observations, graph connectivity, model results, approved KPI values (with T100 decomposition into operational metrics and market indicators) and agent narratives. Every material number links to a product/model release and provenance class. A relationship path is labeled `POTENTIAL_EXPOSURE` until a qualified model quantifies it.

`WorkspaceRequest` includes request ID, model and analytical release IDs, actor/role, channel, purpose, subject scope, branch, graph snapshot, product/evidence release, effective time, knowledge cutoff and query. `InvestigationResult` includes investigation ID, request ID, lifecycle status, branch ID, effective time, knowledge cutoff, pinned release IDs, actor/role, channel, purpose, subject scope and typed cards. Each card carries its own provenance class, epistemic status, recipient availability and access label: assertion with locator; relationship path with edge IDs; quantified result with model and unit; uncertainty; contradiction; unknown; and action proposal with policy outcome. An absent or unauthorized result has the same nondisclosing presentation. A saved investigation pins its releases. Its lifecycle is `OPEN → SAVED|DISCARDED`, `SAVED → SUBMITTED_FOR_REVIEW|CLOSED|DISCARDED`, `SUBMITTED_FOR_REVIEW → CLOSED`; `CLOSED` and `DISCARDED` are terminal; a scenario comparison is a new branch view, not a mutation of baseline.

## 2. Worked interaction

At 10:30 UTC in Scenario A (`SCN-A-T125`, `UC-1`/`UC-4`), a planner opens the affected hydrocracker and sees a graph path to contract K. The interface labels K `POTENTIAL_EXPOSURE`. It displays quantified ULSD yield and margin differences only when a qualified Pyomo/engineering run (`EQ-05`, `EQ-08`, `EQ-09`) and its assumptions are present. The planner compares baseline and derate branches with their model versions and decomposes Margin Capture % into constituent operational metrics and market indicators (T100). A rejected `30,001 bbl/day` feed proposal in `SCN-A-T125` shows the frozen `30,000 bbl/day` compressor-circulation bound (while the separate `SCN-A-H2CONT` sub-case shows its `25,945 bbl/day` shared-$\text{H}_2$ bound), not a fabricated feasible schedule.

The saved noon-correction investigation uses [INFO-001 §3](../03-enterprise-information/PPC-INFO-001_Enterprise_Ontology_Identity_and_Time.md). It pins the reader, channel, purpose and cutoff with its releases. Restricted corrections cannot change counts or placeholder cards. A later screen refresh cannot change the saved result. Duplicate events do not create duplicate alert cards; a failed API call leaves the saved view intact and identifies the unavailable component without leaking protected data.
